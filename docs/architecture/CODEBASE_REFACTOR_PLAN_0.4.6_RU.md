## Первичные результаты аудита

### 1. Слишком крупный UI-модуль

`app/src/main/java/ru/mycapital/app/MainActivity.kt` содержит около 3 584 строк и 206 КБ текста. В одном файле находятся:
- корневая навигация приложения;
- экран главной страницы и график;
- активы и карточка инструмента;
- история операций и фильтры;
- выплаты и календарь выплат;
- события и аналитика;
- диалоги добавления/редактирования;
- форматирование денежных значений;
- часть расчётных функций.

Это главный кандидат на безопасное поэтапное разбиение. Переносить код следует без изменения поведения и публичных контрактов.

### 2. Смешение уровней ответственности

Часть расчётов уже вынесена в отдельные файлы (`AnalyticsCalculations.kt`, `BenchmarkCalculations.kt`, `RealizedTradingCalculations.kt`, `TargetPortfolioCalculations.kt`). При этом расчёт доходности инструмента и некоторые вспомогательные функции всё ещё расположены рядом с UI в `MainActivity.kt`. Нужно провести инвентаризацию и оставить вычисления в независимых от Compose модулях.

### 3. Плоская структура пакетов

Основные файлы UI и расчётов размещены непосредственно в `ru.mycapital.app`, а инфраструктурные классы — в `ru.mycapital.app.data`. Целевая структура должна разделять как минимум:
- `ui/navigation`, `ui/screens`, `ui/components`, `ui/theme`;
- `domain/model`, `domain/calculation`, `domain/usecase`;
- `data/local`, `data/remote`, `data/repository`, `data/import`;
- `core/format`, `core/common`.

Это целевая организация, а не требование одномоментно переместить все файлы. Не создавать абстракции без практической необходимости.

### 4. Репозиторий и источники данных

`PortfolioRepository.kt` содержит существенную бизнес-логику импорта и обработки операций. Клиенты MOEX и другие сетевые клиенты должны иметь единые правила таймаутов, валидации, обработки ошибок и повторных запросов. Сначала требуется карта зависимостей и аудит повторяющихся реализаций; затем — небольшие изменения с тестами.

### 5. База данных и сохранность

`PortfolioDatabase.kt` использует Room schema version 19 и последовательность миграций. Не удалять миграции, не использовать destructive migration и не менять схему ради косметического рефакторинга. Для любого изменения схемы обязательны тесты миграции с реальными предыдущими схемами и сохранностью данных.

## Порядок работ

### Этап 1 — карта кода и защитные тесты
- Составить список экранов, composable-функций, расчётов, источников данных и точек входа.
- Зафиксировать связи между UI, ViewModel/state, repository, DAO и сетевыми клиентами.
- Найти повторяющиеся форматтеры, классификаторы активов и расчётные правила.
- Добавить/уточнить тесты до переноса спорной логики.

### Этап 2 — разбиение MainActivity без изменения поведения
- Вынести навигацию и корневой app state.
- Перенести экраны по одному в отдельные файлы.
- Вынести повторяемые UI-компоненты и диалоги.
- Удалить дублирующие реализации только после подтверждения эквивалентности.
- Не менять визуальный результат и бизнес-логику в рамках чистого переноса.

### Этап 3 — единый domain-слой
- Собрать расчёты портфеля, доходности, FIFO, выплат, бенчмарков и целевых долей в согласованные независимые компоненты.
- Определить единые модели и правила округления/обработки неполных данных.
- Проверить, что разные экраны используют один источник расчётных значений.

### Этап 4 — единый data-слой
- Упорядочить Room DAO/entities, репозитории, MOEX/внешние клиенты, импорт отчётов и резервное копирование.
- Убрать дублирование запросов и правил преобразования.
- Сохранить account-scoping, FIFO, deduplication, корректную обработку незавершённых сделок и исторических позиций.

### Этап 5 — стабилизация и релиз
- Unit tests для затронутой логики.
- Instrumented tests для изменений базы, импорта, восстановления и потоков данных.
- Проверка Release APK и SHA-256 сертификата подписи против исходного сертификата проекта: `77FE78460534AC46DA9A42B03435DEF8CC5D2D6D3CC67C7D3C6C8FD35008FD66`.
- Установка APK поверх 0.4.6 и проверка сохранности локальных данных.
- Только после успешных проверок — следующий номер версии и APK.

## Обязательные правила

1. Маленькие независимые PR, без массового переписывания.
2. Каждый PR основан на проверенной предыдущей точке; зависимости PR явно указаны.
3. `main` не менять и ничего не объединять без отдельного явного разрешения пользователя.
4. Не удалять работающие функции и не менять расчёты в рамках структурного переноса.
5. Не выпускать APK без успешной сборки, необходимых тестов и совпадения сертификата.
6. После каждого этапа фиксировать фактический результат, изменённые файлы, тесты и оставшиеся риски.
