## Правила аудита
- Аудит ведётся от неизменяемой резервной точки.
- На этом этапе исходники приложения не меняются.
- Никаких изменений main и слияний PR.
- Любые последующие исправления — отдельные небольшие коммиты/PR с тестами.
- Перед изменениями схемы Room отдельно проверяется сохранность пользовательской БД.

## Подтверждённые замечания

### E-01. Частичные ошибки источников новостей не переводят синхронизацию в retry/failure
Файлы: app/src/main/java/ru/mycapital/app/data/MarketNewsWorker.kt; MarketNewsClient.kt.
MarketNewsWorker оборачивает получение календаря ключевой ставки, статистики и RSS-новостей в отдельные runCatching. Ошибка конкретного источника превращается в emptyList. Если хотя бы один из трёх источников вернул данные, общий Worker может завершиться Result.success, хотя остальные источники не обновились. Ошибки записываются в progress, но итоговый success summary их не содержит.
Риск: пользователь видит успешное обновление, хотя часть календаря/новостей могла остаться устаревшей; повторная попытка для упавшего источника не планируется.
Рекомендация: хранить результат по каждому источнику (success/empty/error), возвращать retry при временных ошибках, но не удалять/не затирать последнюю успешную выборку; показывать частичный статус в UI. Добавить тесты на комбинации частичного успеха и ошибок.

### E-02. Текущий CI не запускает Android instrumented tests
Файл: .github/workflows/android.yml.
Workflow запускает только testDebugUnitTest, затем assembleRelease и проверку подписи. Два ключевых instrumented набора — PortfolioDatabaseMigrationInstrumentedTest и TwoBrokerAccountsEndToEndInstrumentedTest — не исполняются в CI.
Риск: изменения Room/SQLite и end-to-end поведения могут пройти CI без выполнения Android-тестов.
Рекомендация: добавить отдельный emulator job (или документированную ручную процедуру) для instrumented tests. Сначала оценить длительность и стабильность эмулятора; не блокировать выпуск flaky job до стабилизации.

### E-03. Нет экспортируемых схем Room
Файл: app/src/main/java/ru/mycapital/app/data/PortfolioDatabase.kt.
В аннотации @Database указано exportSchema=false.
Риск: нет версионированных JSON schema snapshots для review изменений и автоматической проверки схем.
Рекомендация: включить exportSchema и хранить схемы в репозитории. Не менять version и не добавлять миграции в рамках этой настройки; проверить генерацию схемы на CI отдельно.

### E-04. Миграционный тест начинается с версии 6
Файл: app/src/androidTest/java/ru/mycapital/app/data/PortfolioDatabaseMigrationInstrumentedTest.kt.
Тест создаёт legacy DB version=6 и прогоняет миграции до текущей версии 19. Миграции 1→5 не проверяются существующим тестом.
Риск: исторические пользователи с очень старыми версиями приложения не имеют полного end-to-end migration regression coverage.
Рекомендация: добавить минимальные fixtures для начальных схем версий 1 и 5 и проверять данные после перехода до 19. Перед этим восстановить точную историческую схему версии 1 из истории Git/релизов; не конструировать её по догадке.

### E-05. Слишком большой корневой файл приложения
Файл: app/src/main/java/ru/mycapital/app/MainActivity.kt.
Файл содержит около 3.4 тыс. строк и совмещает root app state, WorkManager orchestration, navigation и composable screens.
Риск: изменения экранов повышают вероятность побочных эффектов в навигации и общем состоянии; сложнее изолировать тесты.
Рекомендация: после завершения функциональной доработки Events выделять экраны/компоненты постепенно без изменения публичного поведения. Каждый перенос — отдельный небольшой PR с UI/build regression check.


### E-06. Версия базы в механизме резервного копирования отстаёт от Room
Файл: app/src/main/java/ru/mycapital/app/data/PortfolioBackup.kt.
PortfolioDatabase объявляет Room version=19, но PortfolioBackup фиксирует DATABASE_VERSION=14. validateDatabase() требует точного равенства db.version и DATABASE_VERSION. Поэтому экспорт текущей базы версии 19 и восстановление резервной копии, созданной актуальной базой, будут отклонены проверкой версии. Это подтверждённое несоответствие в коде.
Приоритет: КРИТИЧЕСКИЙ для функции резервного копирования/восстановления.
Рекомендация: не просто заменить число на 19. Сначала определить, должна ли резервная копия поддерживать только текущую схему или безопасные старые схемы; согласовать формат manifest и стратегию миграции при восстановлении. Добавить тесты export/restore на актуальной схеме и проверку отката при повреждённом архиве. До исправления не полагаться на встроенный backup/restore как на подтверждённую резервную копию.

## Дополнительные наблюдения по Events
- MarketNewsWorker сохраняет полученные элементы через upsert по sourceKey и чистит записи по updatedAt старше 180 дней. Ошибки отдельных источников не препятствуют очистке старых записей, если хотя бы один источник успешен.
- CorporateEventsWorker защищает кэш от пустого/несовпадающего dividend feed и обновляет данные по совпавшим тикерам внутри транзакций.
- Для облигаций CorporateEventsWorker обрабатывает каждый инструмент отдельно; временная ошибка по одному инструменту не прерывает цикл по остальным.
- В EventsScreen фильтрация выплат отдельного счёта сначала использует accountId из sourceKey, а при его отсутствии — совпадение тикера с текущими позициями. Это fallback-поведение требует отдельного теста для исторических выплат, особенно если одна и та же бумага есть на нескольких счетах.
- В MarketCalendarSection локальная дата и календарные события отображаются в Europe/Moscow. Это соответствует текущей модели событий проекта; отдельно проверить граничные случаи даты/часового пояса.
