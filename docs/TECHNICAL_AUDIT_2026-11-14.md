## Правила аудита
- Аудит ведётся от неизменяемой резервной точки.
- На этом этапе исходники приложения не меняются.
- Никаких изменений main и слияний PR.
- Любые последующие исправления — отдельные небольшие коммиты/PR с тестами.
- Перед изменениями схемы Room отдельно проверяется сохранность пользовательской БД.

## Подтверждённые замечания

### E-01. Частичные ошибки источников новостей не переводят синхронизацию в retry/failure
Файлы: app/src/main/java/ru/mycapital/app/data/MarketNewsWorker.kt; MarketNewsClient.kt.
MarketNewsWorker оборачивает получение календаря ключевой ставки, статистики и RSS-новостей в отдельные runCatching. Ошибка конкретного источника превращается в emptyList. Если хотя бы один из трёх источников вернул данные, общий Worker может завершиться Result.success, хотя остальные источники не обновились. Ошибки записываются в progress, но итоговый success summary их не содержит.
Риск: пользователь видит успешное обновление, хотя часть календаря/новостей могла остаться устаревшей; повторная попытка для упавшего источника не планируется.
Рекомендация: хранить результат по каждому источнику (success/empty/error), возвращать retry при временных ошибках, но не удалять/не затирать последнюю успешную выборку; показывать частичный статус в UI. Добавить тесты на комбинации частичного успеха и ошибок.

### E-02. Текущий CI не запускает Android instrumented tests
Файл: .github/workflows/android.yml.
Workflow запускает только testDebugUnitTest, затем assembleRelease и проверку подписи. Два ключевых instrumented набора — PortfolioDatabaseMigrationInstrumentedTest и TwoBrokerAccountsEndToEndInstrumentedTest — не исполняются в CI.
Риск: изменения Room/SQLite и end-to-end поведения могут пройти CI без выполнения Android-тестов.
Рекомендация: добавить отдельный emulator job (или документированную ручную процедуру) для instrumented tests. Сначала оценить длительность и стабильность эмулятора; не блокировать выпуск flaky job до стабилизации.

### E-03. Нет экспортируемых схем Room
Файл: app/src/main/java/ru/mycapital/app/data/PortfolioDatabase.kt.
В аннотации @Database указано exportSchema=false.
Риск: нет версионированных JSON schema snapshots для review изменений и автоматической проверки схем.
Рекомендация: включить exportSchema и хранить схемы в репозитории. Не менять version и не добавлять миграции в рамках этой настройки; проверить генерацию схемы на CI отдельно.

### E-04. Миграционный тест начинается с версии 6
Файл: app/src/androidTest/java/ru/mycapital/app/data/PortfolioDatabaseMigrationInstrumentedTest.kt.
Тест создаёт legacy DB version=6 и прогоняет миграции до текущей версии 19. Миграции 1→5 не проверяются существующим тестом.
Риск: исторические пользователи с очень старыми версиями приложения не имеют полного end-to-end migration regression coverage.
Рекомендация: добавить минимальные fixtures для начальных схем версий 1 и 5 и проверять данные после перехода до 19. Перед этим восстановить точную историческую схему версии 1 из истории Git/релизов; не конструировать её по догадке.

### E-05. Слишком большой корневой файл приложения
Файл: app/src/main/java/ru/mycapital/app/MainActivity.kt.
Файл содержит около 3.4 тыс. строк и совмещает root app state, WorkManager orchestration, navigation и composable screens.
Риск: изменения экранов повышают вероятность побочных эффектов в навигации и общем состоянии; сложнее изолировать тесты.
Рекомендация: после завершения функциональной доработки Events выделять экраны/компоненты постепенно без изменения публичного поведения. Каждый перенос — отдельный небольшой PR с UI/build regression check.


### E-06. Версия базы в механизме резервного копирования отстаёт от Room
Файл: app/src/main/java/ru/mycapital/app/data/PortfolioBackup.kt.
PortfolioDatabase объявляет Room version=19, но PortfolioBackup фиксирует DATABASE_VERSION=14. validateDatabase() требует точного равенства db.version и DATABASE_VERSION. Поэтому экспорт текущей базы версии 19 и восстановление резервной копии, созданной актуальной базой, будут отклонены проверкой версии. Это подтверждённое несоответствие в коде.
Приоритет: КРИТИЧЕСКИЙ для функции резервного копирования/восстановления.
Рекомендация: не просто заменить число на 19. Сначала определить, должна ли резервная копия поддерживать только текущую схему или безопасные старые схемы; согласовать формат manifest и стратегию миграции при восстановлении. Добавить тесты export/restore на актуальной схеме и проверку отката при повреждённом архиве. До исправления не полагаться на встроенный backup/restore как на подтверждённую резервную копию.

## Дополнительные наблюдения по Events
- MarketNewsWorker сохраняет полученные элементы через upsert по sourceKey и чистит записи по updatedAt старше 180 дней. Ошибки отдельных источников не препятствуют очистке старых записей, если хотя бы один источник успешен.
- CorporateEventsWorker защищает кэш от пустого/несовпадающего dividend feed и обновляет данные по совпавшим тикерам внутри транзакций.
- Для облигаций CorporateEventsWorker обрабатывает каждый инструмент отдельно; временная ошибка по одному инструменту не прерывает цикл по остальным.
- В EventsScreen фильтрация выплат отдельного счёта сначала использует accountId из sourceKey, а при его отсутствии — совпадение тикера с текущими позициями. Это fallback-поведение требует отдельного теста для исторических выплат, особенно если одна и та же бумага есть на нескольких счетах.
- В MarketCalendarSection локальная дата и календарные события отображаются в Europe/Moscow. Это соответствует текущей модели событий проекта; отдельно проверить граничные случаи даты/часового пояса.

### E-07. Файл отката при восстановлении БД копируется до закрытия Room и без WAL
Файл: app/src/main/java/ru/mycapital/app/data/PortfolioBackup.kt; PortfolioDatabase.kt.
В restore() текущий файл my_capital.db копируется в mycapital-before-restore.db до вызова PortfolioDatabase.closeForRestore(). При этом sidecar-файлы SQLite -wal и -shm в rollback-копию не включаются. В WAL mode подтверждённые транзакции могут ещё находиться в WAL и отсутствовать в основном файле базы. Если установка новой базы затем завершится ошибкой, код вернёт rollback-копию основного файла и удалит WAL/SHM целевой базы. В таком сценарии последние подтверждённые изменения пользователя могут не попасть в восстановленную БД.
Приоритет: ВЫСОКИЙ для безопасного отката при неудачном restore.
Рекомендация: сначала корректно остановить доступ к БД и выполнить checkpoint с проверкой результата, затем создавать согласованный rollback snapshot; либо использовать SQLite backup API/другой атомарный механизм, который гарантирует согласованность. Добавить instrumented test, где данные записаны непосредственно перед restore, восстановление намеренно прерывается после начала замены, а затем проверяется сохранность этих данных. Не менять порядок операций без теста на WAL и активные соединения.


### E-08. Ограничение размера HTTP-ответа не защищает от потока с неизвестной длиной
Файл: app/src/main/java/ru/mycapital/app/data/MarketNewsClient.kt, функция readBoundedResponseBody().
Функция отклоняет ответ, если Content-Length больше лимита, затем вызывает source.request(maxBytes + 1), но после этого читает source.buffer.readByteArray(), то есть весь оставшийся поток до EOF. Если сервер не передал Content-Length (contentLength() == -1), тело больше лимита всё равно может быть полностью загружено в память. Это касается HTML/PDF-обогащения карточек новых размещений.
Риск: неожиданный крупный ответ или потоковый ответ без Content-Length может привести к чрезмерному расходу памяти/ошибке OOM, несмотря на заявленный лимит 512 КБ или 4 МБ.
Приоритет: СРЕДНИЙ.
Рекомендация: читать ограниченное число байт через bounded stream/буфер и прекращать чтение сразу после maxBytes + 1; не вызывать readByteArray() для неограниченного остатка. Добавить тесты с неизвестным Content-Length и телом больше лимита, а также с ответом ровно на границе лимита.


### E-09. Ручные финансовые операции не проверяют конечность числовых значений
Файл: app/src/main/java/ru/mycapital/app/data/PortfolioRepository.kt, методы recordTrade(), recordCashFlow(), recordPayout(), confirmPayoutReceived().
Валидация использует сравнения вида quantity > 0, price >= 0, amount > 0, commission >= 0, но не проверяет isFinite(). Для Double положительная бесконечность проходит такие проверки. Например, recordCashFlow(amount = Double.POSITIVE_INFINITY) удовлетворяет amount > 0 и может записать бесконечный баланс; recordTrade/recordPayout также допускают бесконечные значения в денежных полях. NaN часть сравнений отвергается, но это не заменяет явную проверку конечности каждого входа и результата вычислений.
Риск: повреждение денежных остатков, количества активов, средней цены или сумм выплат при некорректном входном значении.
Приоритет: ВЫСОКИЙ для финансовых данных, хотя обычный UI-ввод может ограничивать подобные значения.
Рекомендация: добавить require(value.isFinite()) для всех числовых входов и проверять конечность промежуточных результатов до записи. Покрыть unit-тестами NaN, +Infinity и -Infinity для каждого финансового метода. Не менять существующие округления и правила комиссий в рамках этого исправления.


### E-10. Старые импортированные операции без accountId выпадают из аналитики выбранного счёта
Файл: app/src/main/java/ru/mycapital/app/MainActivity.kt, historyAccountId() и AnalyticsScreen().
Функция historyAccountId() намеренно возвращает null для legacy-ключей SBER:TRADE:... и SBER:CASH:..., так как второй сегмент обозначает тип операции, а не ID договора. При выборе конкретного брокерского счёта analyticsOperations фильтруется строго по historyAccountId(sourceKey) == selectedAccountId. Поэтому legacy-операции, импортированные до введения ключей SBER:<accountId>:..., не попадают в историю сделок выбранного счёта; расчёт реализованного результата и построение истории портфеля по этому счёту могут быть неполными. В PayoutsScreen/AnalyticsScreen для старых выплат без accountId применяется fallback по тикеру текущих активов; если тикер находится на нескольких счетах, такая выплата может отображаться в аналитике обоих счетов.
Приоритет: СРЕДНИЙ, влияет на корректность отчётности по отдельным счетам, но не изменяет общий портфель.
Рекомендация: не назначать legacy-операции счёту по тикеру. Предусмотреть безопасную процедуру сопоставления по исходным брокерским отчётам/периодам или явно показывать блок «не распределено между счетами» и предупреждать о неполной истории. Для выплат без accountId при неоднозначном совпадении показывать как нераспределённые, а не дублировать между счетами. Добавить тесты для legacy и новых sourceKey, двух счетов с одним тикером и ручных выплат без sourceKey.


### E-11. FIFO может смешивать старые импортированные сделки и ручные сделки без accountId
Файлы: app/src/main/java/ru/mycapital/app/RealizedTradingCalculations.kt, PurchaseLotBalances.kt, SaleLotCalculations.kt; data/PortfolioEntities.kt.
OperationEntity содержит отдельное поле accountId, однако brokerAccountIdFromTradeSourceKey() извлекает ID только из ключа нового формата SBER:<accountId>:TRADE:... и не использует поле accountId. Для старых импортированных строк с ключом SBER:TRADE:... результат будет null; для ручных операций без sourceKey — также null. Все они объединяются в одну FIFO-книгу по паре (null, ticker). Поэтому старая импортированная покупка может быть сопоставлена с ручной продажей той же бумаги или наоборот. Существующий тест manualTradesDoNotMatchImportedTradesWithUnknownAccount проверяет только новый scoped sourceKey против ручной операции и не покрывает legacy-формат.
Приоритет: СРЕДНИЙ/ВЫСОКИЙ для точности реализованного результата, особенно при переходе между версиями приложения и смешанном вводе операций.
Рекомендация: определить единый приоритет источника accountId: использовать явное поле OperationEntity.accountId, затем scoped sourceKey; отдельно различать ручные операции, legacy broker imports и операции с неизвестным происхождением. Не объединять две неизвестные группы автоматически. Добавить тесты на SBER:TRADE:... вместе с ручными сделками того же тикера и на миграцию legacy accountId без догадок.
